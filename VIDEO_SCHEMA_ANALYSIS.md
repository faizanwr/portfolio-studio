# Sanity Video Block Schema Analysis

## 1. File/Video Block Schema Definition

### Exact Schema Definition

The video block is defined in `schemaTypes/project.js` (lines 145-178):

```javascript
{
    type: 'file',
    title: 'Video',
    options: {
        accept: 'video/*',
    },
    fields: [
        {
            name: 'hasSound',
            title: 'Audio',
            type: 'boolean',
            description: 'Toggle on if video includes audio (shows mute/unmute controls). Toggle off if video has no audio (hides controls).',
            initialValue: true,
            options: {
                layout: 'checkbox',
            },
        },
    ],
    preview: {
        select: {
            asset: 'asset',
            hasSound: 'hasSound',
        },
        prepare({ asset, hasSound }) {
            return {
                title: hasSound !== false ? 'Video (With Sound)' : 'Video (No Sound)',
                media: asset,
            }
        },
    },
    components: {
        preview: VideoPreview,
    },
}
```

### Key Schema Properties

1. **Type**: `file` (Sanity's built-in file type)
2. **Asset Reference**: ✅ **YES** - The `file` type automatically includes an `asset` reference field
   - The asset reference is stored as `asset._ref` pointing to a Sanity file asset document
   - This is standard behavior for Sanity file types
3. **hasSound Field**: 
   - ✅ **YES** - Boolean field exists
   - **Optional**: No validation rule requiring it
   - **Default Value**: `initialValue: true` (defaults to `true` if not set)
   - **Important**: The preview logic uses `hasSound !== false`, meaning:
     - `undefined` or `null` → treated as "With Sound"
     - `false` → "No Sound"
     - `true` → "With Sound"

### Validation Rules

**⚠️ CRITICAL FINDING: NO EXPLICIT VALIDATION RULES**

The file block has:
- ✅ `accept: 'video/*'` - Browser-level file type restriction in upload UI
- ❌ **NO** `.required()` validation
- ❌ **NO** `.assetRequired()` validation
- ❌ **NO** file size validation
- ❌ **NO** validation that asset exists
- ❌ **NO** validation that uploaded file is actually a video

**This means:**
- File blocks can exist without an asset reference
- No guarantee that `asset._ref` points to a valid asset
- No size limits enforced at schema level

## 2. Video Asset Structure

### Sanity File Asset Metadata

When a file is uploaded to Sanity, the asset document contains:

```typescript
{
  _id: string,           // Asset document ID (e.g., "file-abc123-video-mp4")
  _type: "sanity.fileAsset",
  url: string,           // Direct URL to the file (e.g., "https://cdn.sanity.io/files/...")
  size: number,         // File size in bytes
  assetId: string,      // Asset identifier
  path: string,         // File path
  mimeType: string,     // MIME type (e.g., "video/mp4")
  extension: string,     // File extension (e.g., "mp4")
  // For videos, may also include:
  metadata?: {
    dimensions?: {
      width: number,
      height: number
    },
    duration?: number,   // Video duration in seconds (if available)
  }
}
```

### Video URL Format

Video URLs from Sanity follow this pattern:
```
https://cdn.sanity.io/files/{projectId}/{dataset}/{assetId}.{extension}
```

**Example:**
```
https://cdn.sanity.io/files/slncaqgc/production/abc123-video.mp4
```

### Asset Availability

**⚠️ POTENTIAL ISSUES:**

1. **Missing Assets**: 
   - Asset documents can be deleted from Sanity
   - If `asset._ref` points to a deleted asset, the URL will be invalid
   - The VideoPreview component handles this gracefully (shows "No video uploaded or asset not found")

2. **Non-Video Files**:
   - The `accept: 'video/*'` only restricts the upload UI
   - If a non-video file is somehow referenced, it won't play as video
   - No runtime validation checks the MIME type

3. **URL Format**:
   - URLs are generated by Sanity CDN
   - Should always be properly formatted if asset exists
   - However, if asset is missing, `asset.url` will be `undefined` or `null`

### Video Metadata Extraction

**⚠️ LIMITED METADATA:**

Unlike images (which extract `blurhash`, `lqip`, `palette`, `exif`), videos have:
- ❌ **NO** explicit metadata extraction configured
- ❌ **NO** thumbnail generation configured
- ❌ **NO** duration extraction configured (though Sanity may extract it automatically)

The schema only specifies `accept: 'video/*'` with no metadata options.

## 3. Content Array Structure

### Array Definition

The `content` field is defined as (lines 117-180):

```javascript
{
    name: 'content',
    title: 'Content',
    type: 'array',
    of: [
        { type: 'block' },      // PortableText blocks
        { type: 'image' },      // Image blocks
        { type: 'file' },       // Video blocks
    ],
}
```

### Mixed Content Types

✅ **YES** - The content array can have mixed types:
- Text blocks (PortableText)
- Image blocks
- Video/file blocks

### Order Preservation

✅ **YES** - Arrays in Sanity preserve order
- Items maintain their insertion order
- Reordering in Studio UI updates the array order

### _key Values

✅ **YES** - `_key` values are always present and unique
- Sanity automatically generates `_key` for each array item
- Format: Random string (e.g., `"a1b2c3d4"`)
- Used internally for React key props and array operations
- **Always unique** within the array

## 4. Potential Issues & Recommendations

### ⚠️ Issue 1: Missing Asset Validation

**Problem:**
- File blocks can exist without `asset` reference
- No validation ensures `asset._ref` points to valid asset
- Deleted assets leave orphaned references

**Recommendation:**
```javascript
{
    type: 'file',
    title: 'Video',
    options: {
        accept: 'video/*',
    },
    validation: (Rule) => Rule.required().assetRequired(),
    // ... rest of config
}
```

### ⚠️ Issue 2: hasSound Field Inconsistency

**Problem:**
- `hasSound` defaults to `true` but is optional
- Old data might have `hasSound: undefined` or missing
- Preview logic treats `undefined` as "With Sound" (`hasSound !== false`)

**Current Behavior:**
- `hasSound: undefined` → "Video (With Sound)"
- `hasSound: null` → "Video (With Sound)"
- `hasSound: false` → "Video (No Sound)"
- `hasSound: true` → "Video (With Sound)"

**Recommendation:**
1. Add validation to ensure `hasSound` is always boolean:
```javascript
{
    name: 'hasSound',
    type: 'boolean',
    initialValue: true,
    validation: (Rule) => Rule.required(),
}
```

2. Or migrate existing data to ensure all video blocks have explicit `hasSound` value

### ⚠️ Issue 3: No File Size Validation

**Problem:**
- No maximum file size limit
- Large videos (>50MB) can cause:
  - Slow loading times
  - High bandwidth costs
  - Poor user experience
  - Potential CDN timeout issues

**Recommendation:**
Add file size validation (note: this validates on upload, not in schema):
```javascript
// In Sanity Studio, file size is validated during upload
// Consider adding a note in description:
description: 'Video file (recommended: max 50MB, H.264 codec for best compatibility)',
```

**Alternative:** Use Sanity's Media Library for large videos (supports streaming)

### ⚠️ Issue 4: Malformed or Missing URLs

**Problem:**
- If asset is deleted, `asset.url` will be `undefined`
- VideoPreview component handles this, but frontend code might not
- No validation ensures URL is accessible

**Current Handling:**
The `VideoPreview.jsx` component (lines 14-31) handles missing assets:
```javascript
if (!assetRef) {
    setLoading(false);
    return;
}
// ... fetches asset and checks if asset?.url exists
```

**Recommendation:**
1. Always check for `asset?.url` in frontend code
2. Provide fallback UI for missing videos
3. Consider adding asset existence validation

### ⚠️ Issue 5: Non-Video Files

**Problem:**
- `accept: 'video/*'` only restricts upload UI
- If non-video file is referenced, it won't play
- No runtime MIME type validation

**Recommendation:**
Add custom validation:
```javascript
validation: (Rule) =>
    Rule.custom((file) => {
        if (!file?.asset) return true; // Handled by assetRequired
        // Could add MIME type check if needed
        return true;
    })
```

### ⚠️ Issue 6: No Video Metadata Extraction

**Problem:**
- No thumbnail generation
- No duration extraction
- No dimensions extraction
- Makes it harder to build video previews/thumbnails

**Recommendation:**
Consider using Sanity's Media Library for videos, which provides:
- Automatic thumbnail generation
- Duration extraction
- Streaming support
- Better performance for large files

## 6. Recommendations Summary

### Immediate Actions

1. ✅ **Add asset validation** to file blocks:
   ```javascript
   validation: (Rule) => Rule.required().assetRequired()
   ```

2. ✅ **Make hasSound required** or ensure consistent defaults:
   ```javascript
   validation: (Rule) => Rule.required()
   ```

3. ✅ **Add file size guidance** in description field

### Medium-term Improvements

4. ✅ **Add error handling** in frontend for missing video assets
5. ✅ **Consider migrating** to Sanity Media Library for better video support
6. ✅ **Add data migration** to ensure all existing video blocks have explicit `hasSound` values

### Long-term Considerations

7. ✅ **Monitor video file sizes** and consider compression
8. ✅ **Implement video thumbnails** (may require Media Library)
9. ✅ **Add video format validation** (codec, resolution recommendations)

## 7. Frontend Integration Notes

### How VideoPreview Component Works

The `VideoPreview.jsx` component:
1. Extracts `asset._ref` from the file block
2. Fetches the asset document using Sanity client
3. Extracts the `url` from the asset document
4. Renders a `<video>` element with the URL

**Important:** This is Studio-only. Frontend code should:
- Use Sanity's image/file URL builder if available
- Or construct URLs directly from asset references
- Always check for `asset?.url` existence
- Handle missing assets gracefully

### URL Construction

For frontend use, video URLs can be constructed as:
```javascript
// If you have the asset reference
const videoUrl = `https://cdn.sanity.io/files/${projectId}/${dataset}/${assetId}.${extension}`

// Or use Sanity client to fetch asset
const asset = await client.fetch(`*[_id == $assetId][0]`, { assetId: asset._ref })
const videoUrl = asset?.url
```

## Conclusion

The current schema is functional but lacks validation that could prevent data inconsistencies. The main concerns are:

1. **Missing asset validation** - Could lead to broken video references
2. **Optional hasSound field** - Could cause inconsistent behavior
3. **No size limits** - Large videos could impact performance
4. **No metadata extraction** - Missing thumbnails and duration info

The schema works for basic use cases but would benefit from the recommended validations and improvements.
